# Форк anime4k-webgpu для anion — план улучшений

> Чекбоксы показывают состояние работы. Кто взял этап — отмечает сделанное
> здесь же и коммитит вместе с кодом. Цифры замеров пишутся в «Журнал замеров»
> внизу, а не в чат.

## Зачем

Режимы апскейла в плеере anion (`c`, `ca`) работают на пакете `anime4k-webgpu`
1.0.0 ([upscale.ts](../../anion/src/app/components/custom/anime-page/video-player/upscale.ts)).
Пакет заброшен (последний релиз — июнь 2024), а разбор его исходников нашёл
и баг, теряющий качество, и большой лишний трафик памяти. Форк нужен, чтобы
исправить это у себя, не дожидаясь апстрима.

## Что лежит в репозитории

| Путь | Что это |
| --- | --- |
| `src/` | Код библиотеки. Ветка `main` (до 2026-10-06 — `anion`), remote `upstream` — оригинал. Node ≥ 24. `npm run build` (tsdown) → `lib/`, `npm run check` — TypeScript 7 + oxlint. |
| `conversion/` | Генераторы шейдеров (`cnn.py`, `artcnn.py`, `generate.sh`) и их исходники в `conversion/glsl/` (Anime4K, ArtCNN — копии, MIT). |
| `bench/` | Стенд: время по звеньям пресета и попиксельная сверка с эталоном. |
| `bench/baseline/`, `bench/ref/` | Эталоны: бандл 1.0.0 из npm и снимки `lib/` после этапов (`ref/e8` — ворота повторов, до упаковки). Локальные, в `.gitignore`. |

Проверено: сборка форка из исходников даёт те же 288 шейдеров, что и бандл в
npm, байт в байт (разница только в CRLF и именах минификатора). Значит,
исходники в `src/` — это ровно то, что сейчас работает в плеере.

### Стенд

```bash
npm run bench
```

Открыть `http://localhost:5179/bench/` в Chrome. Без файла стенд берёт
синтетический кадр с JPEG-артефактами; лучше подложить настоящий кадр или
ролик с Kodik (720p, это потолок Kodik). Поля таблицы:

- **поток, мс/кадр** — кадры подряд без ожидания, ближе к реальному плееру.
  **Основная метрика**, ускорение считается по ней.
- **GPU, мс** — сумма звеньев по `timestamp-query`, медиана и p95. На Apple
  метки между проходами ненадёжны (тайловый GPU перекрывает проходы), и
  стенд прячет их, если они идут не по возрастанию. Им не доверять.
- **сверка** — `maxΔ` и PSNR выхода кандидата против эталона. Для правок, не
  меняющих математику (Э2, Э5 без f16), норма — `maxΔ < 1/255`.

В логе — цена каждой стадии кандидата (ClampHighlights, DenoiseCNNx2VL, …),
посчитанная как разность потоковых замеров префиксов цепочки. Шум ±0.5 мс.
Бюджет кадра: 41.7 мс при 24 к/с.

> Кандидат (форк, ESM) грузится через `import()` в `bench/bench.js`; эталон —
> UMD-бандл 1.0.0 из `bench/baseline/`. Перед замером — `npm run build`.

## Что нашёл разбор (исходные данные для плана)

**Цепочки пресетов** (`src/pipelines/presets/ModeC|ModeCA/index.ts`):

- `ModeC`: ClampHighlights → DenoiseCNNx2VL (в исходном разрешении) → Downscale
  (если цель < 2×) → CNNx2M (если цель > 2.4×).
- `ModeCA`: то же, плюс CNNM (восстановление) **в целевом** разрешении.
- При цели ≤ 1.2× исходника `ModeC` не делает ничего, кроме ClampHighlights.

**Цена**, посчитанная по шейдерам:

| Звено | Проходов | MAC/px | Где считается |
| --- | --- | --- | --- |
| ClampHighlights | 3 | ~0 | исходник |
| DenoiseCNNx2VL | 17 conv + DepthToSpace + Overlay | ~8 500 | исходник |
| CNNx2M / CNNM | 8 conv + 2 / 8 conv | ~2 100 | вход звена |

720p при 24 к/с: ModeC ≈ 380 GFLOPS, ModeCA ≈ 590 GFLOPS.

**Проблемы:**

1. **ClampHighlights — пустая операция.** Порт считает максимум яркости 5×5
   по *тому же* кадру и делает `min(luma, max)`. Окно включает сам пиксель,
   так что разница всегда 0. В оригинале
   (`conversion/glsl/anime4k/Anime4K_Clamp_Highlights.glsl`) статистика
   собирается на исходнике (`HOOK MAIN`), а зажим стоит на `HOOK PREKERNEL`,
   то есть **после** всех увеличений. Он гасит светлые ореолы (ringing) от CNN.
   Сейчас ореолы не гасятся, а 3 прохода тратятся впустую. Баг во всех шести
   пресетах.
2. **Трафик памяти.**
   - Каждый слой 3×3 разбит на два шейдера (`tf`, `tf_1`), и оба читают одни и
     те же входы.
   - Последний слой 1×1 — три шейдера, и *каждый* читает все 14 промежуточных
     текстур `rgba16float`.
   - DepthToSpace и Overlay идут отдельными проходами.
   - Оценка для 720p: около 735 МБ на кадр (~17 ГБ/с при 24 к/с). Для
     встроенной GPU с общей памятью это главный тормоз.
3. **Шейдеры без тайлинга и f16.** Каждый пиксель сам читает 9 соседей из
   каждой входной текстуры, вся арифметика в f32. ArtCNN (`conversion/glsl/artcnn/`)
   уже написан правильно: shared memory, f16, 16 каналов упакованы в 2×2
   текселя. Это образец.
4. **Бандл.** Один UMD-файл на 3.4 МБ со всеми 288 шейдерами. anion нужны
   только ModeC/ModeCA — это около 350 КБ исходников шейдеров. Из-за UMD
   в anion появился костыль `unwrapPresets`.

- [x] ModeC/ModeCA: зажим слит с последним звеном — `ClampStats` (статистика

      Без увеличения (цель ≤ 1.2×) ModeC отдаёт вход как есть — зажим там
      тождество. Сверка с прежней сборкой: maxΔ 0.12/255; M1 Pro: −0.2…1 мс

### Э2. Слияние проходов — математика та же, памяти втрое меньше

Сделано новым генератором `conversion/cnn.py` (старый `shader.py` остался
для моделей, которые anion не использует). Генератор строит модель сети из
GLSL и выпускает стадии + `model.ts`; исполнитель — общий `helpers/CNN`.
Перегенерация моделей anion — `conversion/generate.sh`.

- [x] **2a.** Пары `tf` + `tf_1` с одинаковыми входами → одна стадия с двумя
      `textureStore`; входы читаются один раз.
- [x] **2b.** Три шейдера последнего слоя 1×1 → один с тремя выходами.
- [x] **2c.** Последний слой + DepthToSpace + Overlay → один проход: поток
      пишет 2×2 пикселя выхода, `textureSampleLevel` исходника + residual.
- [x] Перегенерированы DenoiseCNNx2VL, CNNx2M, CNNM; все стадии модели — в
      одном compute-проходе.
- [x] Готово: DenoiseCNNx2VL — 8 проходов вместо 19. Сверка с `ref/e1` без
      16 px у края — maxΔ 0.12–0.25/255.
      **Края изменены намеренно:** координаты прижимаются к краю, как `texOff`

### Э5. Ядра: тайлинг и f16

Владелец: целевое железо — M1 / современный iGPU, Э5 не обязателен.

- [x] Генератор умеет плитку в shared memory (`CNN_TILE=1`) и блок пикселей
      на поток (`CNN_BX`, `CNN_BY`) — переключатели для замеров. На M1 Pro оба
      вредят: плитка −17%, блок 2×1 и больше — в 4–5 раз медленнее (регистры
      вытесняются в память). По умолчанию выключены.
- [x] f16: шейдер пишет типы через псевдонимы `T4/M4/A4`, `helpers/CNN`
      объявляет их для f32 или f16 (`enable f16`) — один шейдер на оба варианта,
      бандл не растёт. Опция `precision: 'f16'` в ModeC/ModeCA (нужна фича
      `shader-f16` у устройства). Смешанный вариант (произведения f16, суммы
      f32) — 0.55× из-за приведений, поэтому f16 — целиком.
      Сверка f16 с ref/e2: maxΔ ≤ 1.31/255, PSNR ≥ 68 дБ — в допуске.
- [x] Соседи 3×3 через subgroups (`CNN_SUBGROUPS=1`): свой пиксель — из
      текстуры, соседи — `subgroupShuffle` с проверкой индекса потока
      (раскладку WebGPU не гарантирует). Математика та же (maxΔ 0.125/255), но
      на M1 Pro медленнее: VL 15.2 → 21.5 мс, CNNM 2.9 → 6.5 мс — текстурный кэш
      Apple отдаёт соседей дешевле. Выключено, оставлено для замера на iGPU.
- [ ] Готово, когда: +20–50% к Э2 хотя бы на одной встроенной GPU, без регрессии
      на дискретной. **M1 Pro: f32 +3–10% (вес — одна константа в `let`),
      f16 0.92–1.08×** — у Apple f16 той же скорости, что f32. Решение по f16
      по умолчанию — после замера на Intel/AMD iGPU (там f16 вдвое быстрее).

### Э8. Пропуск повторяющихся кадров

В аниме много кадров подряд с тем же рисунком (анимация «на двойках»,
статичные планы), а цепочка считала каждый заново. Худший случай (сцена
с движением) не меняется — выигрыш в средней нагрузке: нагрев, шум, батарея.

- [x] `helpers/FrameGate`: проход сравнения кадра с последним посчитанным
      (max |Δ| в уровнях 8 бит, `atomicMax`) → один поток пишет аргументы
      косвенного запуска всех звеньев (шаблон или нули) → копия кадра в
      опорный — тоже косвенно, только когда кадр считается. CPU ничего не ждёт.
- [x] Звенья ModeC/ModeCA (`CNN`, `ClampStats`, `Downscale`) получают `gate` и
      запускаются через `launcher()` — `dispatchWorkgroupsIndirect`. Без
      `gate` — прежний прямой запуск.
- [x] Опции пресетов `skipUnchanged` (по умолчанию выключено) и
      `unchangedThreshold` (по умолчанию 0 — только точные повторы, выход тот
      же, что без ворот). Счётчики — `preset.gate.readStats()`.
- [x] Стенд: флажок «пропуск повторов» (на неподвижном кадре — цена повтора)
      и «Прогнать ролик»: ролик без ворот и с ними, доля повторов, время
      кадра, гистограмма max |Δ| для выбора порога.
- [x] Проверено на стенде (M1 Pro, тестовый ролик x264: 8 с «на двойках» +
      4 с статичного плана, 285 кадров): ворота нашли 92 точных повтора,
      ffmpeg (`framemd5`) — 95 из 288; время кадра 19.06 → 14.24 мс в
      среднем. Сверка с `ref/e8` с воротами — та же, что без них (maxΔ

### Э16. «Детали»: Winograd F(2×2, 3×3) — отброшен

Лаборатория `bench/lab/wino.mts` (локально): внутренние 8 слоёв 24→24 —
Winograd, первый и хвост — ядро `fast` из `src`. Веса G g Gᵀ считаются в f32
из f16 и округляются в f16: 16 матриц на пару групп вместо 9 (18 КБ на слой).
Поток — плитка 2×2 выхода и часть выходных групп, тайл `[группа][пиксель]`.
Сверка с эталоном конвертера: **точнее `fast`** — 67.5 дБ и maxΔ 2.0/255
против 65.2 дБ и 3.2/255 (меньше округлений в f16 на выход).

Время (Chromium 152, панель скрыта, только сеть 720p, вперемешку с ядром
Э14, 2 повтора, мс): ядро Э14 40.3–43.1; плитка × 1 группа (192 потока)
47.4–47.6; то же с построчным входным преобразованием 44.8–47.1 (лучший);
× 2 группы 51.7–54.9; × 3 группы 110; 2 плитки на поток 70–76; 4 плитки
271 (wgpu); веса группы в общей памяти 54.6–58.6; накопители f32 227.

Почему: умножений в 2.25 раза меньше, но матрица весов позиции идёт только на
одну плитку — чтений весов на выход в ~7 раз больше, чем у прямого ядра, где
матрица отвода идёт на 4 пикселя (Э14 показал, что упор — в чтения весов).
Вернуть повторное использование можно только несколькими плитками на поток, а
это 16 накопителей на плитку и группу — регистры кончаются (70+ мс). Через
общую память (позиции ↔ плитки, как batched GEMM) нужны десятки КБ на группу
— больше лимита 16 КБ. Не пробовать снова без матричных инструкций
(`subgroup-matrix`) или другого повода.

### Итоги Э19–Э20 и что дальше

Выводы (2026-10-28, после выкладки U48-3):

- **По точности «Максимальное» почти исчерпано, и упор не в число
  параметров.** На тех же порченых кадрах val лучшие внешние модели дают
  28.4–28.7 дБ (AnimeSharpV4 Fast, JaNai SD strong, AniSD PLKSR — 3–10 с на
  кадр), U48-3 — 28.22 за ~28 мс. Ёмкость в сотни раз больше даёт ~0.5 дБ;
  цель «+20%» (~1 дБ по MSE) недостижима даже для них — в кадре Kodik после
  x264 этой информации нет.
- **Кривая по размеру пологая.** u32x10 (0.61 SUC по умножениям) против
  u48x7 (0.96 SUC) — 27.84 против 27.97 дБ (Э19): +56% счёта дали 0.13 дБ.
  u48x9 (~214k, ~37 мс на M1 Pro при бюджете 41.7) по той же кривой дал бы
  сотые доли дБ и съел весь запас.
- **Реальные шаги давала цель обучения, не сеть:** учитель Compact (Э19 —
  фон и штрих), штрих U48-2 с порченого входа (Э20 — +0.33 дБ, меньше
  дорисовок). Повторить такой шаг ещё раз учителем — вряд ли: у составной
  цели уже лучшее из доступных моделей.
- **Ровный фон — от функции потерь, а не от размера.** Фактуру по порченому
  входу не угадать; L1 к цели в таких местах минимизируется средним по
  вариантам — гладкой «акварелью». Поэтому фактура SD не перешла в ученика
  ни в одном из двух прогонов Э20, и большая сеть с тем же L1 мазала бы так
  же. PSNR этот перекос поощряет (Kodik v1 в Э19: 28.26 дБ при деталях 0.82),
  так что как главный ориентир он дальше бесполезен.

Что пробовать, когда будет M5 Pro (ожидается ~середина ноября 2026; обучение
и прогоны учителей станут быстрее, параллелить, может быть, можно будет без
перегрева):

- [x] **Потери на фактуру** — та же u48x7, к L1 добавить сравнение
      статистик ВЧ по участкам (СКО/спектр полосы σ0.75–3 против цели) или
      лёгкий дискриминатор (GAN) с малым весом. Единственный путь к живому
      фону без роста цены кадра. Риск — выдуманная фактура мерцает между
      кадрами: проверять на роликах Kodik (мерцание — разница соседних
      выходов на статичных планах против входа), не на стоп-кадрах. Начать с
      дешёвого: статистики ВЧ, без GAN.
- [x] **Несколько кадров на входе** — единственный источник настоящей новой
      информации: x264 портит соседние кадры по-разному, на статичных планах
      их можно усреднить. Первый слой шире (6–9 каналов вместо 3), остальное
      как было. Нужны пары из видео (последовательности, а не одиночные
      кадры), выравнивание по движению или хотя бы маска статики, правки в
      ядре и в плеере (держать прошлый кадр). Долгое исследование на
      несколько этапов без гарантии; начать с оценки: сколько дБ даёт
      усреднение двух кадров на статичных планах Kodik без всякой сети.
      **Оценка (2026-10-31) — не стоит делать.** 30 кадров `data/val`, вход
      ×½ с `soften 0.7`, клип из 7 кадров через x264 с настройками Kodik,
      PSNR к чистому входу, средний кадр (B) против среднего соседних:
      - статичный план: 97–99.5% пикселей B-кадра бит в бит совпадают с
        соседним (блоки skip) — усреднение 2/3/7 кадров даёт 0.00 дБ на CRF
        24/32/40; с зерном σ2 и энкодом релиза до Kodik — то же (98.9%);
      - панорама 1/2/4 px за кадр с **точным** выравниванием (целый сдвиг):

### Э21. Дебандинг до сети

Дизеринг в blit (Э3) не даёт полос при выводе в 8 бит, но полосы x264 в самом
исходнике (небо, дым, тёмные сцены, затемнения) сеть видит как ступеньки и
сохраняет. Решение владельца (2026-10-31): в anion — всегда в «Максимальном» и
«Сильном», без пункта в меню.

- [x] Звено `Deband` (`src/pipelines/denoise/Deband`), как deband в mpv: на
      пиксель 4 отсчёта на случайном радиусе (до `range` × i), замена средним,
      если max |Δ| по RGB меньше `threshold` / i; дальше — плавно на нет к
      двойному порогу. Без зерна (сеть приняла бы его за фактуру). Случайность —
      PCG от координаты, не от времени: на статичном плане узор не кипит. Выход
      rgba16float. Запуск из ворот: на повторе пропускается вместе с сетью.
- [x] `ModeCompact`: `deband?: boolean | { threshold, range, iterations }`,
      в библиотеке по умолчанию выключен (выход как в 1.x). По умолчанию
      `threshold` 2 уровня, `range` 16, `iterations` 2. Стенд — флажок
      «дебандинг» и поля параметров.
- [x] Подбор на копии шейдера в numpy (тот же PCG и билинейная выборка) и
      U48-3 в PyTorch (`it100000`), 51 кадр Kodik и синтетический градиент
      ночного неба через `degrade.x264_roundtrip`, CRF 28:
      - Градиент: после сети без дебандинга — широкие полосы с рваным краем и
        цветными пятнами блоков, дизеринг Байера их не прячет; с дебандингом
        — гладко уже при пороге 2 (2, 3 и 4 на глаз одинаковы).
      - Кадры Kodik: пятна макроблоков на заливках U48-3 и так почти
        выглаживает — на 1:1 разницы не видно, только при контрасте ×4.
        Фактура (ВЧ на участках со СКО 2–10 без контуров) ×1.01 при пороге 2,
        ×1.05 при 3; контуры сдвигаются на 0.04 уровня. При пороге 4 пропадает
        слабая фактура фона (Overlord) — выше 2–3 не поднимать.
      - Жёсткий порог (как в mpv) оставлял одиночные точки на сглаженной
        заливке; сеть их размывает, но мягкий спад безопаснее.
- [x] Стенд (M1 Pro, Chromium 152 в приложении, 720→1080, u48x7 — сеть
      U48-3, `fast`, σ2, 100 итераций, вперемешку): без дебандинга 32.00 /
      32.56 мс/кадр, с ним 32.43 / 32.56 — в шуме; стадия Deband 0.29 мс.
      (CompactSR 31.2 против 27.8–28.7 в Э19 — состояние машины, не правка.)
- [x] Мерцание: 48 кадров подряд `bench/ref/kodik-like-overlord.mp4` с 30 с,
      среднее max |Δ| соседних кадров по RGB на статике (вход расходится
      ≤ 3 уровней): вход 0.878 → с дебандингом 0.870; через U48-3 (участок
      256×256, 86% статики, 16 пар) 0.608 → 0.578. Не добавляет, чуть гасит.
- [x] anion: `deband: true` в `compactPreset` (`upscale.ts`), библиотека
      v1.1.0-anion.11 — anion `7c20117` (2026-10-31).

### Э24. Нечётные стороны кадра у половинной сетки

Владелец (2026-10-31): на 480p «Максимальное» падало — «CompactSR: кадр

- [x] Проверка на GPU (Chromium 152, U48-3, σ2): 1280×720 → 2560×1440 и →
      1920×1080 против релиза v1.1.0-anion.11 — maxΔ 0 (бит в бит); 853×480

      края), NaN нет. На стенде — сценарий 853→1706×960. Чтение выхода — через

      сравнила нули с нулями).
- [x] Время: старая (v1.1.0-anion.11) и новая библиотека вперемешку, U48-3
      720→1440, 60 кадров потоком × 4: новая 33.33 / 31.94 / 32.26 / 32.59,
